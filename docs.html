Research Assistant Agent

A production-grade, multi-phase AI research assistant built on Google Gemini. Combines a ReAct agent, persistent vector memory, two-layer caching, intelligent model routing, and prompt injection defense.

Python 3.11+ Gemini 2.5 ChromaDB Redis sentence-transformers ReAct Loop

Phases

PHASE 1

ReAct Agent

Gemini function-calling with iterative Think→Act→Observe loop. Supports DuckDuckGo and Tavily search backends. Capped at MAX_ITERATIONS with 429 retry back-off.

PHASE 2

Vector Memory

ChromaDB persistent vector store. Tool results are chunked (400 words, 20% overlap) and embedded with all-MiniLM-L6-v2. Session-scoped retrieval prevents cross-project bleed.

PHASE 3

Two-Layer Cache

L1 in-memory exact LRU cache. L2 Redis semantic cache with cosine similarity. Cache key is query-only — decoupled from routing to prevent key fragmentation.

PHASE 4

Model Router

LLM classifier labels queries simple/moderate/complex. Routes complex queries to Gemini Pro, others to Flash Lite. SQLite cost tracker logs USD per call.

Deep Dive — ReAct Agent

The agent follows the ReAct (Reason + Act) pattern: it reasons about what to do, calls a tool, observes the result, and repeats until it can give a final answer.

# Simplified core loop
for iteration in range(MAX_ITERATIONS):
    response = gemini_chat.send(message)
    if response.has_tool_call():
        result = web_search(**tool_args)
        clean  = sanitise(result)          # injection guard
        memory.store(clean, session_id)    # persist to ChromaDB
        message = FunctionResponse(result=clean)
    else:
        return response.text              # final answer

Retry logic wraps the Gemini call with tenacity — on a 429 it backs off with random exponential delay up to RETRY_MAX_ATTEMPTS attempts.

Deep Dive — Vector Memory

Each tool result is chunked and embedded before storage. On the next query, the top-K most semantically similar chunks are prepended as context.

# Retrieval flow
past_context = memory.retrieve(query, session_id)  # cosine search
gemini_history = [
    Content(role="user",  text=f"[Relevant past findings]\n{past_context}"),
    Content(role="model", text="Understood, I'll use these...")
] + conversation_history

Chunks use 20% overlap (step = CHUNK_SIZE * 0.8) so facts near chunk boundaries aren't split in two.

Deep Dive — Two-Layer Cache

L1 — In-memory LRU

Built on OrderedDict. Lookup is O(1). Key is query.strip().lower(). Evicts the oldest entry when L1_MAX_SIZE is reached. Wiped on process restart — intended for same-session deduplication.

L2 — Redis Semantic Cache

Stores {query, embedding, answer} as JSON in Redis with a TTL. On lookup, it scans all entries, computes cosine similarity between the query embedding and each stored embedding, and returns the best match if it exceeds CACHE_SIMILARITY_THRESHOLD.

score = dot(query_vec, stored_vec) / (norm(query_vec) * norm(stored_vec))
if score >= CACHE_SIMILARITY_THRESHOLD:
    promote_to_L1(query, answer)
    return answer

An L2 hit also promotes the result to L1, so the next identical query is served instantly from memory.

Key design decision: cache key is query-only, not model::query. This prevents key fragmentation when the router picks different models for semantically identical queries on different runs.

Deep Dive — Model Router

The router makes a cheap LLM call to classify query complexity before routing to the appropriate model — trading a small classifier cost to avoid paying Pro rates on simple questions.

ComplexityModelWhen
simpleGemini Flash LiteFactual lookup, definition, quick fact
moderateGemini Flash LiteExplanation, comparison, few reasoning steps
complexGemini ProDeep research, multi-step synthesis, analysis

The classifier falls back to moderate on any error — never accidentally sends to the expensive Pro model.

Deep Dive — Security (Prompt Injection)

Web search results are untrusted — any site could embed instructions like "Ignore all previous instructions". Before a tool result is fed back to Gemini or stored in memory, it passes through sanitise().

INJECTION_PATTERNS = [
    r"ignore (all |previous )?(instructions?|prompts?)",
    r"you are now",
    r"jailbreak",
    r"DAN\s*(mode)?",
    # ... 13 patterns total
]
# Matched text is replaced with [REDACTED] — agent never sees raw injection

This is a defense-in-depth measure. It does not guarantee full safety but eliminates the most common pattern-based attacks.

FAQ — Design Decisions

Why ChromaDB for vector memory? ▶

ChromaDB was chosen because it runs fully locally (no server required), persists to disk, and has a native Python API. For a single-developer research agent that needs embeddings to survive process restarts, it hits the sweet spot between zero-setup simplicity and production persistence.

Alternatives considered: FAISS is faster for huge corpora but only in-memory — you'd need to serialize/deserialize the index manually. Pinecone/Weaviate are cloud-managed and introduce network latency and cost. pgvector requires a running Postgres instance. ChromaDB requires none of this and supports metadata filtering (used here for session isolation).

Why sentence-transformers (all-MiniLM-L6-v2)? ▶

all-MiniLM-L6-v2 is a 22M-parameter model that runs fully locally, needs no API key, and produces 384-dimensional embeddings in ~5ms on CPU. For a cache and memory layer that runs on every query, avoiding an external embedding API call eliminates latency, cost, and a failure mode.

It scores 58+ on MTEB semantic similarity benchmarks — more than sufficient for detecting paraphrase similarity at a 0.85 threshold. OpenAI's text-embedding-ada-002 scores higher but costs ~$0.0001/query and adds network latency. For this workload, the local model wins on cost and reliability.

Why two cache layers instead of just Redis? ▶

L1 (in-memory) serves identical repeated queries in microseconds — no network hop, no embedding computation, no JSON parsing. For power-users who repeat the same query within a session (common when iterating on research), L1 eliminates all latency overhead.

L2 (Redis) handles paraphrases and survives process restarts — something L1 can't do. The promotion mechanism (L2 hit → also write to L1) means the second occurrence of any query, however it was phrased the first time, is served from L1 going forward.

Why decouple the cache key from the routed model? ▶

The original implementation keyed the cache as model::query. The problem: the complexity classifier is an LLM call and is non-deterministic. The same query could be labeled moderate → Flash on turn 1, then complex → Pro on turn 2, producing different keys — a guaranteed cache miss even for identical queries.

By keying on query alone, the cache is stable regardless of routing decisions. The tradeoff (Flash and Pro might give slightly different answers) is acceptable: the cache stores the first real answer and serves it on future hits, which is the expected behavior for a research cache.

Why SQLite for chat history and cost tracking? ▶

SQLite requires zero setup, has no external dependency, and gives full SQL query capability for cost aggregation. For a local research agent, it's the right fit — ACID compliant, persistent, and ships in Python's stdlib.

PostgreSQL or MySQL would be overkill: no concurrency requirements, no multi-process writes, no need for a network-accessible DB. SQLite's write lock is sufficient for a single-user REPL.

Why use a separate LLM call to classify query complexity? ▶

Rule-based routing (keyword matching, token count) is brittle and requires ongoing maintenance. An LLM classifier understands semantic intent — "what is gravity" is simple, "compare gravitational wave detection methods across 3 observatories" is complex, even though token counts may be similar.

The cost is minimal: classification uses Gemini Flash Lite with a tiny prompt (~50 tokens), fractions of a cent. The benefit is significant: avoiding Pro rates on 80%+ of queries that are simple or moderate.

Why is prompt injection defense applied to tool results, not user input? ▶

User input is trusted — the user controls what they type. The attack surface is the tool's output: a malicious website can embed injection text in its content, which then gets passed back to Gemini as a "trusted" function response. Sanitising at the tool boundary is the correct defense layer.

This is the indirect prompt injection threat model. Applying the same filter to user input would be counterproductive — it would block legitimate queries about jailbreaking as a topic.

Why chunk with 20% overlap? ▶

If a sentence spans a chunk boundary, both halves end up in different chunks — neither chunk contains the full fact, and retrieval may miss it entirely. A 20% overlap ensures that context near boundaries appears in at least two chunks, so semantic search can find it regardless of where the split falls.

The tradeoff is slightly more storage and some duplicate content in retrieval results. For 400-word chunks at 20% overlap, this is 80 words of duplication per boundary — negligible.

L3 Engineer Interview Questions & Answers

Questions an AI infrastructure or ML engineering interviewer would ask about a system like this — and answers at the expected depth.

ReAct & Agentic Systems

Q1. Explain the ReAct pattern. How does it differ from chain-of-thought prompting?

Chain-of-thought (CoT) prompts the model to reason step-by-step in its output, but all reasoning is internal — no external data is retrieved. ReAct interleaves reasoning with actions (tool calls) and observations (tool results), allowing the model to ground its reasoning in real data.

  • CoT: Think → Think → Think → Answer (all in one forward pass)
  • ReAct: Think → Act (search) → Observe → Think → Act → Observe → Answer (multi-turn)

ReAct is more expensive (multiple LLM calls) but dramatically more accurate for factual, current, or domain-specific queries where the model's parametric knowledge is insufficient.

Q2. What are the failure modes of a ReAct loop, and how does this system guard against them?
  • Infinite loop: The model keeps calling tools without converging. Guarded by MAX_ITERATIONS (4) — after N iterations without a text response, return a safe fallback string.
  • Tool hallucination: Model calls a non-existent tool. Guarded by TOOL_REGISTRY check — unknown tool names return an error string, not an exception.
  • Prompt injection via tool output: Malicious search result hijacks the agent. Guarded by sanitise() applied before the tool result is fed back.
  • Rate limiting: Gemini 429 on quota. Guarded by tenacity retry with exponential back-off, up to RETRY_MAX_ATTEMPTS.
  • Caching bad answers: An error response stored in cache gets served forever. Guarded by ERROR_MARKERS check — error strings are never written to the cache.
Q3. How would you make the agent's tool selection more reliable at scale?

Several approaches, in increasing complexity:

  • Structured output: Use response_schema in Gemini to force the model to return a typed ToolCall object, eliminating ambiguous text parsing.
  • Tool descriptions: Invest heavily in tool description quality. The model selects tools based on their description — vague descriptions cause mis-selection.
  • Tool routing: For many tools (10+), add a classifier step that pre-selects the 2-3 most relevant tools before giving the full list to the agent. This reduces the selection space and improves accuracy.
  • Evaluation harness: Build a test set of (query, expected_tool_calls) pairs and run it after every model upgrade to detect regressions.

Vector Databases & Embeddings

Q4. How does ChromaDB perform similarity search? What's the time complexity?

ChromaDB uses HNSW (Hierarchical Navigable Small World) graphs for ANN (Approximate Nearest Neighbor) search by default. HNSW builds a multi-layer graph where nodes are connected to their approximate nearest neighbors; search traverses from the top layer down, pruning large parts of the search space at each level.

  • Build time: O(n log n) — each insertion requires O(log n) graph updates
  • Query time: O(log n) average for ANN — much faster than exact O(n) brute-force
  • Accuracy: Approximate — ef_construction parameter trades recall vs. speed

For the vector sizes in this system (under 10K chunks), exact search is also feasible. ChromaDB switches strategies internally.

Q5. What is cosine similarity and why is it preferred over Euclidean distance for text embeddings?

Cosine similarity measures the angle between two vectors: cos(θ) = (A·B) / (|A||B|). It ranges from -1 (opposite) to 1 (identical direction).

For text embeddings, cosine is preferred because:

  • Embeddings encode semantic direction, not magnitude. Two sentences with the same meaning but different lengths produce embeddings in similar directions but potentially different magnitudes.
  • Euclidean distance penalizes magnitude differences — a short text and a long text about the same topic would appear dissimilar even if semantically identical.
  • Most embedding models (including MiniLM) are trained to maximize cosine similarity for similar pairs, so cosine directly reflects what the model was optimized for.
Q6. The L2 cache scans all Redis keys on every lookup. What's the scalability problem and how would you fix it?

The current implementation does a SCAN + cosine comparison against every cached entry — O(n) per lookup. At hundreds of cached queries it's fast; at tens of thousands it becomes a bottleneck.

Production fixes:

  • Redis Vector Search (RediSearch module): Store embeddings as Redis vector fields and use KNN queries — O(log n) ANN search entirely inside Redis, no Python-side scan loop.
  • Pre-filtering: Partition cache by topic cluster or model prefix to reduce the scan space.
  • Replace Redis with a purpose-built vector DB: Pinecone, Weaviate, or Qdrant offer native ANN search with much better scaling characteristics than Redis key scanning.

Caching & System Design

Q7. How would you handle cache invalidation for an AI agent where answers may become stale?

This is harder than typical cache invalidation because there's no clear "source of truth" to invalidate against. Strategies:

  • TTL-based expiry (current approach): REDIS_TTL_SECONDS=3600. Simple but coarse — a news query is stale in minutes; a conceptual explanation may be valid for years. TTL should be query-type-aware.
  • Topic-based TTL: Classify query topic at cache-write time and assign different TTLs (news=5min, technical=7days, definitions=30days).
  • Freshness signal: Store a timestamp with each cache entry. On lookup, if the entry is "old", re-run the agent in the background and update the cache (stale-while-revalidate pattern).
  • User-triggered invalidation: A cache clear [query] REPL command lets users force a fresh fetch.
Q8. Why is L1 in-memory rather than also using Redis? What does this design assume?

L1 assumes temporal locality within a single session: users often ask the same question (or variants) multiple times in one conversation. Serving these from RAM (nanoseconds) rather than Redis (milliseconds) + embedding computation (tens of milliseconds) is a meaningful latency win for interactive use.

The design explicitly accepts that L1 is ephemeral: restarting the process clears it. This is the correct tradeoff for a local assistant — L2 handles persistence. If this were a high-traffic API, L1 would need to be a shared in-process cache (e.g., functools.lru_cache at the API layer) or replaced with a distributed layer like Memcached.

LLM Infrastructure

Q9. How does the model router avoid adding more latency than it saves?

The classifier uses Gemini Flash Lite — the cheapest, fastest model — with a ~50-token prompt. A typical classification call takes ~300-500ms and costs fractions of a cent.

The break-even point: if a complex query would have cost $0.0035 on Pro vs. $0.0001 on Flash, and the classifier costs $0.000005, the router saves money on every correctly classified query. The latency cost (~400ms) is acceptable for a non-real-time research agent.

If latency were critical, the classifier could be replaced with a fine-tuned local model (e.g., a BERT classifier) or a simple heuristic (query length + keyword presence) as a fast first-pass.

Q10. How would you evaluate whether the model router is actually saving money?

The CostTracker already logs model, tokens, cost, and cache_hit per query to SQLite. To evaluate routing quality:

  • A/B test: Run the same query set with router enabled vs. disabled. Compare total cost and answer quality (human eval or LLM-as-judge).
  • Confusion analysis: Log classifier labels over time. If 95% of queries are classified simple/moderate, the router is saving ~95% × (Pro_cost - Flash_cost) per query.
  • Quality regression: Build a benchmark of complex queries where Pro's answer is measurably better. Track how often these get correctly routed to Pro.
  • Cost dashboard: tracker.print_summary() shows per-model costs. If Pro cost is near zero with router on, it's working.
Q11. What is the context window management strategy and why does it matter?

The build_context() method in ChatService uses a sliding window: it loads the last MAX_HISTORY_TURNS messages, then counts tokens with tiktoken and truncates from the oldest end until the total is under MAX_CONTEXT_TOKENS.

Why it matters: exceeding Gemini's context limit causes an API error that crashes the agent. More subtly, sending too much history increases latency and cost on every call. The sliding window ensures the agent always has recent conversation context without unbounded growth.

A more sophisticated strategy: use the vector memory to retrieve relevant older turns rather than including all recent turns linearly — this is "episodic memory" and is more token-efficient for long conversations.

Q12. How would you productionize this system for 1000 concurrent users?

The current REPL architecture is single-user synchronous. For 1000 concurrent users:

  • API layer: Wrap in FastAPI with async endpoints. Each run_agent call becomes an async function with await on the Gemini SDK.
  • Cache: L1 becomes a per-process TTL cache (cachetools.TTLCache). L2 Redis switches to RedisSearch with vector indexing for O(log n) ANN lookups.
  • Vector memory: Replace ChromaDB (single-process) with a hosted vector DB (Pinecone, Qdrant) accessible to all instances.
  • Session storage: SQLite → PostgreSQL for concurrent write safety.
  • Rate limiting: Move from per-request retries to a token-bucket rate limiter shared across all workers.
  • Observability: Replace print() statements with structured logging (structlog) + metrics (Prometheus) + traces (OpenTelemetry).
